# План: система подготовки к IT-собеседованиям

> **Reference, not instructions.** Read on demand — when you need the reasoning behind a
> decision, the phase gates, or what was cut and why. The rules you must follow every
> session are in `AGENTS.md` and `.harness/1-instructions/CONSTRAINTS.md`, which are kept short on purpose.

## Context

Исходный `prompt.md` описывает продукт «всё и сразу»: 10 направлений × 5 уровней × 3 языка × 6+ режимов, плюс маркетинг, биллинг и SEO. Репозиторий пустой — greenfield.

Три проблемы исходной постановки:

1. **Объём контента нереален.** ~150 качественных вопросов на ячейку (направление × уровень) = ~7 500 вопросов на язык, ~22 500 на три. LLM сгенерит за вечер, но ценность даёт ревью: ~3 мин/вопрос ⇒ ~375 часов только на английский.
2. **У банка вопросов нет moat.** «Сгенерируй 20 вопросов по React senior с разбором» — бесплатно в любом чате. Плюс бесплатные GitHub-репы держат SEO-верх. Платят за то, чего чат не даёт: **состояние во времени** (интервальные повторения), **калибровку уровня** ответа, **план вместо ленты**, **данные рынка**.
3. **«Свежесть на сентябрь 2026» — обязательство, а не фича.** Устаревают не вопросы, а версии и мода (React 19, Next 15, Node 22, вопросы про AI-ассистентов). Нужен конвейер обновления либо честный отказ от обещания.

**Решения, принятые с пользователем:**
- Приоритет — сначала свой оффер, продукт после.
- Ниша №1 — senior/staff fullstack + platform (полный охват ниже).
- Форм-фактор публичного запуска — Chrome-расширение, всё локально, плюс минимальный статический сайт под чекаут и SEO.
- Жёсткого дедлайна по собесам нет.

**Ожидаемый результат:** личный тренажёр, по которому пользователь реально готовится и получает оффер; его контент и процесс становятся ядром публичного продукта без переписывания.

## Harness — как это исполняется

Основная работа Фазы 0 — длинный однородный цикл с машинно-проверяемым результатом (180 статей, 660 вопросов, всё под схемой). Именно тот случай, где ограниченная рабочая среда для агента окупается.

### Принятые решения

| Вопрос | Решение | Почему |
|---|---|---|
| Граф или цикл | **Граф внутри единицы работы, цикл над очередью** | По критериям применимости графа проект набирает 4 из 5; не выполняется пятый — «выгода координации > накладных расходов» |
| Уровень зрелости цикла | **Уровень 3** (разделение maker/checker). Уровни 4–5 — нет | Узкое место — человеческое ревью; параллельный флот его не ускоряет, а только раздувает очередь |
| WIP | **1 активный элемент** + противодавление очереди ревью | Дробление внимания даёт незавершённую работу; это же подтверждают бенчмарки курса |
| Инициализация | **Отдельная фаза 0.0** до любого контента | Инициализация и реализация оптимизируют разное; смешение даёт видимый код вместо фундамента |
| Кто закрывает задачу | **Харнесс по команде верификации; контент — человек** | Субъективная уверенность агента заменяется исполняемым доказательством |

**Оркестрационный налог здесь решающий.** Узкое место проекта — **твоё ревью**: оно не параллелится и агенту запрещено. Десять авторских узлов наполняют очередь ревью в десять раз быстрее, чем ты её разгребаешь. Это Goodhart в чистом виде: «статей сгенерировано» растёт, «статей проверено» стоит. Граф, оптимизирующий генерацию, оптимизирует не то.

### Фаза 0.0 — инициализация

Отдельная фаза, до первой статьи. Четыре артефакта:

1. Запускаемое окружение с зафиксированными зависимостями (`package.json`, `.nvmrc`)
2. Работающий тестовый фреймворк и **хотя бы один проходящий тест**
3. Bootstrap-контракт: как запустить, как проверить, из чего состоит проект
4. `feature_list.json`, разложенный на элементы с критериями приёмки

**Gate:** *холодный старт* — свежая сессия отвечает на «как запустить» и «как проверить» **только по содержимому репозитория**, без устных пояснений. Не отвечает — карта неполная, фаза не закрыта.

### Репозиторий как единственный источник правды

Чего нет в репозитории — для агента не существует.

| Файл | Роль | Лимит |
|---|---|---|
| `AGENTS.md` | Маршрутизатор: что за проект, как запустить, как проверить, ссылки на тематические доки | ≤ 200 строк, цель ~100 |
| `.harness/1-instructions/CONSTRAINTS.md` | Жёсткие MUST / MUST NOT | **≤ 15 пунктов** |
| `docs/*.md` | Тематические: схема контента, протокол ревью, правила расширения, RAG-eval, лицензии | 50–150 строк каждый |
| `ARCHITECTURE.md` | В каждом пакете: ответственность, интерфейсы, ограничения | — |
| `PROGRESS.md` | Состояние между сессиями: коммит, статус тестов, блокеры, следующий шаг | — |
| `DECISIONS.md` | Что решили, почему, что отвергли | — |
| `Makefile` | Единая поверхность команд: `setup`, `test`, `lint`, `check` (обёртки над pnpm) | — |
| `feature_list.json` | Очередь работы | — |

Один разросшийся файл инструкций не работает: он съедает 8–15% контекстного окна, важное тонет в середине, и всё выглядит одинаково важным. Отсюда лимиты в таблице. Правила живут **рядом с кодом**, к которому относятся, а не в общей свалке.

### Пятнадцать жёстких запретов (`.harness/1-instructions/CONSTRAINTS.md`)

Ровно столько, сколько влезает в рабочую память. Первые шесть проверяются в CI.

1. Не проставлять `review_status: reviewed` — **никогда**
2. Не редактировать лицензии в `content/sources.yaml`
3. Не создавать вопрос без `wiki_refs` и `sources`
4. Не создавать вопрос без стоящей за ним статьи вики
5. Не оставлять `TODO`, `test.skip`, пустой `expected_answer[]`, пустой `naive_approach`
6. Не коммитить секреты и `.env`
7. Не объявлять элемент готовым без запуска его команды верификации
8. Не держать больше одного активного элемента
9. Не генерировать контент, когда очередь ревью заполнена
10. Не добавлять элементы в `feature_list.json` — область работ принадлежит человеку
11. Не рефакторить до прохождения верификации
12. Не запрашивать широкие host-permissions в манифесте расширения
13. Не отправлять данные пользователя никуда, кроме его собственного эндпоинта
14. Не подключать удалённый код в расширении
15. Не переносить `реализовано` в отчёт без ссылки на evidence

### `feature_list.json` — схема и машина состояний

Каждый элемент: `id`, `behavior` (наблюдаемый результат), `verification` (исполняемая команда), `state`, `evidence` (вывод команды).

```
not_started → active → blocked → passing
                  ↑         ↓
                  └─────────┘
```

- **Состояние меняет харнесс, не агент.** Единственный путь в `passing` — прохождение команды верификации
- Для контента добавлено состояние `human_review` **после** `passing`: машинные проверки прошли, но закрывает элемент человек
- Размер элемента — «закрывается за одну сессию». Одна статья, один батч вопросов, один пакет кода

### Цикл

1. Взять один `not_started` (**WIP = 1**)
2. Выполнить
3. Запустить команду верификации из самого элемента
4. Прошло → `passing` (контент → `human_review`). Упало → `blocked`, причина в `PROGRESS.md`, цикл останавливается
5. **Противодавление:** очередь `human_review` больше N (≈15, объём одного захода ревью) — генерация встаёт до разбора. Единственный механизм, не дающий разогнать бессмысленную метрику

Протокол сессии: на входе — прочитать `PROGRESS.md` и `DECISIONS.md`, прогнать `make check`; на выходе — обновить `PROGRESS.md`, прогнать `make check`, закоммитить. Цель — старт сессии за минуты, а не за полчаса восстановления контекста.

### Граф внутри единицы работы

```
research (официальные источники)
   ↓
author (статья)
   ↓
fact-check ──veto──► назад в author
   ↓
generate-questions (из готовой статьи)
   ↓
validate (make check, eval-наборы) ──fail──► назад
   ↓
human_review   ← агент дальше не идёт
```

`fact-check` **обязан быть отдельным узлом с независимым контекстом**: писавший статью её не проверяет. То же правило раздельных проходов, что в `CLAUDE.md` (`Never self-approve in the same active context`).

Четыре обязательных вопроса перед тем, как рисовать граф:
- *Кто владеет целью* — человек; агент берёт из `feature_list.json` и не дополняет его
- *У кого veto* — `fact-check` по фактам, `validate` по схеме, человек на `human_review` окончательно
- *Что может двигаться, что заморожено* — счётчик `draft` свободен, счётчик `reviewed` двигает только человек
- *Кто кого питает* — статья питает вопросы; вопрос без статьи не создаётся

**Фаза 1 (код) — обычный цикл**, без графа: разработка расширения не делится на независимые единицы так же чисто.

### Три уровня верификации

Пропуск любого уровня = не завершено.

1. **Статика:** схема Zod, линт, типы
2. **Поведение:** юнит-тесты, eval-наборы (оценщик, RAG, газеттир, DSA)
3. **Сквозной прогон:** реальная сессия тренажёра из чистого состояния; для Фазы 1 — установка собранного расширения и прохождение сценария в браузере

Третий уровень ловит то, к чему первые два слепы: рассогласование схемы между CLI и расширением, разъезд поисковых бэкендов, битые ссылки вики после переименования.

**Архитектурные правила — исполняемые, а не документированные.** «Расширение не ходит в сеть, кроме эндпоинта пользователя» — это лог-правило, падающее на `fetch` к чужому хосту, а не абзац в доке.

**Сообщения об ошибках пишутся для агента:** что упало, почему это важно, что конкретно сделать. «`expected_answer` содержит один пункт — оценщик не сможет различить уровни; разбей на 3–5 независимых пунктов с `min_level`» вместо «invalid schema».

### Промоция замечаний ревью в правила

Самый ценный механизм для этого проекта. Каждое **повторяющееся** замечание при ручном ревью превращается в автоматическую проверку в `make check` и строку в `docs/review-rules.md`.

Отклонил три статьи за отсутствие версии технологии в утверждении — появилась проверка. Отклонил вопросы за пересекающиеся пункты `expected_answer` — появилась проверка. Очередь ревью со временем чистится сама, а это прямой удар по узкому месту проекта.

### Наблюдаемость

- **Рубрика качества контента** (A–D по осям: фактическая точность, привязка к версии, качество источников, независимость пунктов ответа, глубина под уровень). Она же — контракт узла `fact-check` и она же делает ревью воспроизводимым
- **Журнал пропускной способности:** сколько сгенерировано против сколько отревьюено за период. Если разрыв растёт — узкое место подтверждено, WIP-лимит надо снижать, а не поднимать
- **Трасса элемента:** какие узлы отработали, где был откат, сколько попыток. Без неё повторные прогоны — блуждание вслепую

### Чистое состояние на выходе

Чек-лист выхода из сессии: сборка проходит, тесты проходят, `feature_list.json` обновлён, отладочного мусора нет, стандартный путь запуска работает.

Раз в месяц — **аудит упрощения харнесса**: отключить один компонент, прогнать бенчмарк. Не просело — удалить. Ограничение, осмысленное три месяца назад, сегодня может быть чистыми накладными расходами.

### Что переиспользовать

OMC уже даёт цикл и состояние: `ralph` / `autopilot` / `ultrawork`, `.omc/state/`. Свой раннер не писать — специфичны только контракт (`AGENTS.md`, `.harness/1-instructions/CONSTRAINTS.md`, `feature_list.json`) и запреты выше. Для проектирования — навык `context-engineering:harness-engineering`.

**Побочная выгода:** домен `agentic` в банке вопросов — ровно про это. Строя продукт харнессом, получаешь для него контент из первых рук, а не пересказ чужих статей.

## Предметный охват Фазы 0

Это **одно** направление, а не десять — senior/staff fullstack с платформенной глубиной. Так объём становится посильным: ~660 отревьюенных вопросов вместо 22 500.

| Домен | Что входит | Ориентир, вопросов |
|---|---|---|
| `dsa` | Основа: Big O, time/space complexity. Плюс ~20 паттернов: sliding window, two pointers, fast/slow, binary search, BFS/DFS, backtracking, DP, greedy, heap/top-K, union-find, topological sort, intervals, prefix sum, monotonic stack, trie, bit manipulation, k-way merge, subsets, matrix, linked-list | отдельные сущности, см. ниже |
| `frontend` | React 19, Next.js 15 (RSC, кэширование, роутинг), shadcn/ui, производительность, состояние | 60 |

| `architecture` | DDD, Clean, Hexagonal, Vertical Slice — границы, трейд-оффы, когда что | 50 |
| `backend-node` | NestJS, микросервисы, serverless, V8 isolates / Cloudflare Workers, Supabase, Vercel | 70 |

**Веса — предварительные.** Их пересчитывает карта частотности из реальных вакансий (шаг 2 конвейера ниже) **до** массовой генерации. Она же разрешает пары, которые не спрашивают вместе (Terraform vs Pulumi, три облака, три брокера): данные покажут, какой домен заслуживает 60 вопросов, а какой 10. Готовиться ко всем поровну — гарантированно размазаться.

`system-design` — не отдельная тема, а **интегратор**: сценарии ссылаются на вопросы из `messaging`, `data`, `caching`, `network`. Именно эта связность отличает senior от staff-ответа, и именно её схема должна поддерживать (`related_questions[]`).

**DSA моделируется отдельно** — это не Q&A, а практика. Три сущности:

**1. `concept` — фундамент по сложности (must have, изучается первым).**
Не справочная таблица, а объяснение + тренируемый навык:
- что такое Big O, чем отличается от Θ и Ω, зачем нужна асимптотика
- **time vs space** отдельно, включая скрытую память: рекурсивный стек, аллокации, копии срезов
- амортизированная сложность (push в динамический массив, rehash в хеш-таблице) — типичная дыра на собесе
- **как распознать сложность по форме кода**: вложенные циклы → O(n²); деление диапазона пополам → O(log n); цикл с рекурсией → дерево рекурсии; два указателя по одному проходу → O(n); сортировка внутри → нижняя граница O(n log n); почему `.includes()` в цикле незаметно даёт O(n²)
- сложности операций базовых структур (массив, хеш-таблица, куча, дерево, граф) — таблицей, но как справка к предыдущему пункту, а не вместо него

**2. `pattern` — ~20 паттернов.**
Поля: название, **признаки распознавания «когда применять»** (по формулировке задачи), шаблон решения, целевая сложность, типичные ошибки, `related_concepts[]`, курируемый список задач.

**3. `task` — курируемая задача со ссылкой на LeetCode/NeetCode.**
Ключевая часть — **обязательная пара подходов**:
- `naive_approach`: идея, сложность, **почему именно упирается** (TLE на каком размере входа, какая избыточная работа повторяется)
- `optimal_approach`: идея, сложность, **key insight** — та одна мысль, которая переводит из наивного в оптимальный
- `delta`: что изменилось между ними и на какой паттерн это указывает

Дельта между наивным и оптимальным решением — и есть обучающая единица. Голое оптимальное решение не учит: на собесе от кандидата ждут именно перехода «вот брутфорс за O(n²), теперь ускоряю до O(n) вот так».

Свой судья задач не пишем — конкурировать с LeetCode бессмысленно, ценность в курировании пути и в тренировке распознавания.

---

## Ключевое архитектурное решение

**Контент отделён от доставки.** Вопросы живут как структурированные файлы в репозитории со схемой и валидацией в CI. CLI-тренажёр (Фаза 0), Next.js-сайт (Фаза 1) и любой будущий канал (Telegram, расширение) — просто рендереры одного и того же `content/`.

Это снимает блокирующий вопрос «во что упаковать»: решение принимается позже и обратимо.

Без дедлайна главный риск — вылизывать инфраструктуру и не готовиться. Поэтому у каждой фазы есть **gate**: пока он не пройден, следующая не начинается.

## Фаза 0 — личный тренажёр

**Gate начала тренировок:** статьи вики + по 15 отревьюенных вопросов на 3 самых весомых домена. Не ждать полного банка — начинать тренироваться с первого же домена.
**Gate выхода в Фазу 1:** ~180 статей вики + ~660 отревьюенных вопросов + фундамент по сложности + 20 DSA-паттернов с ≥5 задачами (naive + optimal) на каждый + пройдено минимум 3 реальных собеседования.

### Структура репозитория

```
content/                       # источник истины, не зависит от приложений
  wiki/{domain}/*.md           # слой знаний: Markdown + frontmatter, из него растёт всё
  questions/{domain}/*.yaml
  dsa/concepts/*.yaml          # Big O, time/space complexity — свои схемы
  dsa/patterns/*.yaml
  dsa/tasks/*.yaml             # naive + optimal подходы, ссылка на LeetCode
  domains.yaml                 # дерево доменов + веса по данным рынка
  sources.yaml                 # реестр внешних источников + лицензии
  tech-aliases.yaml            # газеттир: канон технологии → алиасы, для разбора вакансий
packages/schema/               # Zod-схемы + CLI-валидатор
packages/rag/                  # чанкинг, индекс, поиск, eval-набор
packages/importer/             # импорт готовых банков: GitHub-репы, md-файлы
packages/pipeline/             # ingest вакансий, генерация, очередь ревью
apps/drill/                    # Фаза 0: CLI-тренажёр + SQLite прогресса
apps/extension/                # Фаза 1: Chrome MV3, бандл контента + IndexedDB
apps/site/                     # Фаза 1: статический сайт — SEO, лендинг, чекаут

Makefile                       # setup / test / lint / check
```

Стек: TypeScript, pnpm workspaces, Zod, `better-sqlite3`, `yaml`. Всё локально, без сервера.

Nx здесь **не** брать: воркспейс из четырёх пакетов его не окупает. Nx — тема банка вопросов, а не инструмент этого проекта.

### Wiki + RAG — слой знаний

**Вики первична, вопросы вторичны.** Статьи — источник истины по фактам; вопросы генерируются из них и ссылаются на них. Это решает проблему свежести из `prompt.md`: поддерживать нужно ~180 статей, а не 660 вопросов. Обновил статью (React 19 → 20) — всё, что на неё ссылается, автоматически помечается `needs_review`.

**Формат.** `content/wiki/{domain}/{slug}.md` — Markdown, git-tracked, с YAML-frontmatter: `slug`, `title`, `domain`, `topic`, `tech: {name, version_range}`, `levels[]`, `summary`, `prerequisites[]`, `related[]`, `sources[]`, `review_status`, `reviewed_at`. Перекрёстные ссылки — `[[slug]]`.

`prerequisites[]` даёт граф порядка изучения — это и есть «режим обучения» из `prompt.md`, без отдельной разработки.

**Чанкинг.** По заголовкам (H2/H3). Чанк несёт `{doc_slug, heading_path, domain, topic, tech_version}` и является одновременно единицей поиска и единицей цитирования.

**Retrieval — поэтапно, не начинать с векторов:**
- **Этап 0:** SQLite **FTS5** (BM25) + структурные фильтры по домену/теме/уровню. Корпус ~180 статей ≈ 2 000 чанков — лексический поиск с фильтрами закрывает большинство запросов. Детерминированно, без инфраструктуры, тестируемо.
- **Этап 1 (только если замеренный recall недостаточен):** добавить эмбеддинги в `sqlite-vec` и объединить с BM25 через **RRF** (reciprocal rank fusion). Модель эмбеддингов — **локальная, без API-ключа**: при нулевом бюджете платный embedding API даёт стоимость на каждый запрос пользователя, а на корпусе в 2 000 чанков локальная модель по качеству не уступает. По-прежнему один файл SQLite, без внешнего сервиса.
- **Реранкер** — только если и слияния не хватило.

Векторная БД на старте — типичная преждевременная сложность: на таком корпусе BM25 с фильтрами обычно выигрывает, а отладить его на порядок легче.

**Почему не CodeGraph и не `codebase-memory-mcp`.** Оба индексируют **символы кода** — функции, классы, импорты, графы вызовов, IaC-манифесты; прозу и Markdown не индексируют по замыслу. Вики продукта — текст о технологиях, поэтому ни один из них не заменяет `packages/rag`. Их архитектура ретривера (SQLite + FTS5 + опциональные локальные эмбеддинги, MIT) подтверждает выбранный подход и годится как ориентир при реализации.

Реальное место для такого индексатора — Фаза 2 (отбор файлов при разборе репозитория) и Фаза 3 (задания по чужому коду). Но и там в браузере полноценный граф не построить: хватает файловых эвристик, при необходимости `tree-sitter` в wasm. Сейчас — не нужен вовсе.

**Что обслуживает RAG:**
1. **Режим обучения** — читать теорию, спрашивать «объясни X», получать ответ с цитатами
2. **Заземление оценщика** — на каждый непокрытый пункт `expected_answer` дать ссылку на конкретный раздел вики: «не хватило про backpressure — вот здесь»
3. **Генерация вопросов** grounded в вики, а не в весах модели — отсюда и согласованность с ответами, и заполненные `sources`
4. **Карта слабых мест → план обучения**: слабые домены разворачиваются в список статей в порядке `prerequisites`

**Жёсткое правило против галлюцинаций:** ответ в режиме обучения обязан цитировать чанки. Нет релевантных чанков — «в базе этого нет, вот что почитать», а не генерация по памяти. Иначе продукт превращается в тот самый чат, от которого мы отстраиваемся.

**OMC-скилл `wiki` для этого не подходит:** `.omc/wiki/` git-ignored и project-local, поиск без эмбеддингов, содержимое не версионируется вместе с вопросами. Он годится для заметок *о ходе проекта* (решения, отладка), но не для контента продукта. `packages/rag` пишется свой — он всё равно нужен Фазе 1 на сервере.

### Схема вопроса

Один вопрос — один YAML-файл. Поля:

- `id`, `slug`, `lang`
- `domain`, `topic`, `subtopic`
- `tracks: [fullstack, backend, frontend]`, `levels: [middle, senior, staff]`
- `tech: { name, version_range }` — версия отдельным полем, это то, что протухает
- `question`
- `expected_answer` — **массив пунктов**, каждый с `text`, `weight`, `min_level`. Не сплошной текст: пункты нужны машинной оценке
- `follow_ups[]` — вопросы «со звёздочкой» из `prompt.md`
- `common_mistakes[]`
- `related_questions[]` — связь доменов с `system-design`
- `wiki_refs[]` — статья + якорь раздела, откуда вопрос выведен; несёт `wiki_reviewed_at` для отслеживания расхождения
- `sources[]` — ссылки на официальные доки/RFC
- `difficulty`, `estimated_minutes`
- `review_status: imported | draft | reviewed | verified`, `reviewed_at`
- `provenance` — для импортированных: источник, путь, коммит

`review_status` — критичное поле. В тренировку и на публичный сайт попадает только `reviewed` и выше; `imported` и `draft` — рабочие состояния. Валидатор в CI это проверяет.

### Конвейер наполнения (vacancy-driven)

1. **Ingest вакансий** (djinni.co, DOU, LinkedIn) → извлечь требуемые технологии и уровень.
   ⚠️ Проверить ToS каждого источника. Приоритет: официальные API/RSS/ручной экспорт. Скрейпинг в обход ToS — юридический риск для коммерческого продукта; решить это сразу, а не после запуска.
2. **Карта частотности** → `content/domains.yaml`. Задаёт и порядок твоей подготовки, и порядок генерации. Делается **первой**, до массовой генерации.
3. **Написание статей вики** по весам, домен за доменом. Это основная работа: ~180 статей.
4. **Генерация вопросов из статей** — grounded в конкретных разделах, с проставленными `wiki_refs` и `sources`.
5. **Очередь ревью** — CLI показывает черновик рядом с разделом-источником, ты правишь/принимаешь/отбрасываешь, ставится `reviewed`. Ревью быстрее, потому что факт уже проверен на этапе статьи.

Шаг 2 — то, чего нет у конкурентов, и он же позже бесплатно закрывает режим «под вакансию» из `prompt.md`.

Для подготовки под конкретную вакансию **переиспользовать существующий навык `interview-prep-from-jd`** — он уже делает разбор JD в prep-pack, не дублировать.

### Импорт готовых банков (GitHub-репы, md-файлы)

Самый быстрый способ засеять банк и, главное, **обнаружить пробелы**: чего в твоей вики ещё нет.

**Лицензии — блокирующее условие, решается до первого импорта.** Публичные репы с вопросами лицензированы очень по-разному, и для коммерческого продукта разница критична:

| Лицензия | Можно ли |
|---|---|
| MIT / Apache-2.0 / CC-BY | Да, с указанием авторства |
| CC-BY-SA | Вирусная: производный контент обязан быть share-alike — конфликтует с платными фичами |
| CC-BY-NC | **Нет.** Коммерческое использование запрещено |
| Лицензии нет | **Нет.** Отсутствие лицензии = все права защищены |

Поэтому `content/sources.yaml` — реестр источников: `{id, name, url, kind: github|md|dir, license, license_verified_at, commercial_ok, attribution_required, commit}`. **CI блокирует импорт из источника с `commercial_ok: false` или неизвестной лицензией.** Решать это на старте дешевле, чем вычищать контент после запуска.

**Конвейер импорта:**

1. **Адаптеры источников:** GitHub-репа (клон на зафиксированный коммит), директория с md, одиночный файл.
2. **Парсеры — per-source, не универсальный.** Форматы этих реп различаются: `## Вопрос` + `<details><summary>`, нумерованные списки, таблицы, пары `Q:`/`A:`. Один «умный» парсер на всех даст мусор; конфиг парсинга хранится рядом с источником.
3. **Нормализация** в черновые сущности с `provenance: {source_id, path, anchor, commit, imported_at}` и статусом `imported`.
4. **Дедупликация.** Эти репы сильно пересекаются между собой. Нормализовать текст (регистр, пунктуация, код) → триграммная Жаккарова близость или SimHash → пары выше порога уходят на слияние, а не добавляются молча.
5. **Переписывание, а не копирование.** Импортированный элемент — это **зацепка, а не готовый контент**: LLM переформулирует вопрос и строит `expected_answer[]` **по твоей вики**, а не по тексту источника. Это одновременно чинит качество (ответы в таких репах часто устарели и поверхностны) и снимает вопрос перепубликации чужого текста.
6. **Ручное ревью** — как обычно, `imported → reviewed`.

**Побочный эффект, ради которого стоит импортировать даже неподходящие по лицензии репы (только для чтения, без включения в контент):** импортированные вопросы, не ложащиеся ни на одну статью вики, дают **карту пробелов** — какие темы нужно написать.

**DSA:** списки вроде Blind 75 / NeetCode 150 импортируются как `task`-заглушки (название + ссылка); `naive_approach`/`optimal_approach` пишутся своими руками. Перечень названий задач со ссылками — факты с низким копирайт-риском, но ToS площадки проверить.

**CLI:** `pnpm import --source=<id>` и `pnpm import:refresh` — перечитать источник на новом коммите и показать дифф.

### Тренажёр (`apps/drill`)

- Отбор: фильтр по домену/уровню + очередь повторений
- **Интервальные повторения — SM-2.** Это и есть «progress tracking» и половина «системы мотивации» из `prompt.md`. Стрики и бейджи не нужны.
- Режим свободного текстового ответа (позже — голосом, ближе к реальному собесу)
- Три отдельных режима для `dsa`, все в общей очереди повторений:
  - **распознавание сложности**: показать фрагмент кода → назвать time и space → сверка с разбором формы кода
  - **распознавание паттерна**: показать формулировку задачи → назвать паттерн и целевую сложность → сверка
  - **naive → optimal**: назвать наивное решение и его сложность, потом key insight и оптимальное; решение пишется по ссылке на LeetCode
- Прогресс в SQLite: `reviews(question_id, answered_at, score, ease, interval, next_due)`

### Оценщик ответов

Ядро ценности. Не «вот правильный ответ», а:

1. LLM сопоставляет ответ с `expected_answer[]` → по каждому пункту `covered | partial | missing`
2. Из покрытых пунктов и их `min_level` выводится **оценка уровня**: «ответ тянет на middle, до senior не хватило X и Y»
3. Каждый непокрытый пункт сопровождается **цитатой из вики** через `wiki_refs` — не «ты не знаешь backpressure», а конкретный раздел для чтения
4. Агрегация по доменам → **карта слабых мест** и план обучения: слабые домены разворачиваются в статьи в порядке `prerequisites` (пункт из `prompt.md`, закрывается как побочный эффект схемы)

Рубрика по пунктам, а не «оцени от 1 до 10» — иначе оценки невоспроизводимы и калибровка бессмысленна.

## Фаза 1 — Chrome-расширение (основная поверхность) + статический сайт

**Gate входа:** пройден gate Фазы 0.

### Почему расширение, и что оно даёт на самом деле

Правильная причина делать расширение — **не** «легче продвигать», а то, что оно умеет работать **в контексте**, чего сайт не может в принципе:

- **Оверлей на LeetCode/NeetCode:** открыта задача → расширение показывает карточку паттерна, подсказку по сложности и разбор naive → optimal. Это самая ценная и самая «расшариваемая» фича продукта.
- **Захват вакансии на LinkedIn/djinni/DOU:** открыто объявление → извлекается стек → мгновенно собирается план подготовки из твоего банка. Это режим «под вакансию» из `prompt.md` в родной среде.

**Разбор гипотезы «локально без внешних API легче продвигать»:**

| Утверждение | Оценка |
|---|---|
| Легче пройти ревью в Chrome Web Store | **Верно.** MV3 запрещает удалённый код в принципе; без host-permissions и без декларации сбора данных ревью быстрее и предсказуемее |
| Легче продвигать | **Неверно.** Ранжирование в CWS — установки, оценки, свежесть, ключевые слова. Архитектура не участвует |
| Скрытая цена | Поиск в CWS на порядки меньше веб-поиска, и расширение **обнуляет SEO** — единственный бесплатный канал с накоплением |

Обе фичи выше требуют host-permissions на конкретные сайты, так что «совсем без разрешений» не выйдет — но запрашивать нужно **узко и по одному домену**, а не `<all_urls>`: это главный фактор длительности ревью.

### Захват вакансии со страницы

Ключевая фича расширения и прямая реализация режима «под вакансию» из `prompt.md`.

**Поток:**

1. **Определение страницы.** Content-script на поддерживаемых площадках (djinni, DOU, LinkedIn, hh, Indeed). Адаптер на площадку с селекторами + generic-фолбэк по основному тексту, когда разметка не совпала.
2. **Извлечение — газеттиром, без LLM.** `content/tech-aliases.yaml`: канон → алиасы (`kubernetes: [k8s, к8с]`, `postgres: [postgresql, pg, постгрес]`). Сверх сопоставления:
   - **секции**: «Требования / Must have / Required» против «Будет плюсом / Nice to have» → вес обязательного выше желательного
   - **уровень**: из заголовка и паттернов стажа («5+ years», «от 5 лет»)
   - **отрицания**: «не требуется», «not required» — иначе технология попадёт в план наоборот
3. **Матчинг на банк.** Технологии → домены → вопросы и статьи, ранжированные по весу из вакансии **и по твоей слабости** из данных SM-2. Пересечение «важно для вакансии» × «плохо знаю» — это и есть план.
4. **Артефакт подготовки** сохраняется локально: темы, план на N дней, очередь вопросов, ссылки на статьи вики.
5. **Дельта покрытия** — технологии из вакансии, которых нет в банке. Показывается пользователю честно («это не покрыто») и одновременно **работает как сигнал тебе**, что писать дальше.

**Правовой статус здесь принципиально иной, чем у ingest вакансий в Фазе 0.** Расширение читает страницу, которую пользователь уже открыл, в его браузере, для его личного использования — это не серверный скрейпинг площадки. Вопрос ToS, поднятый в конвейере Фазы 0, для этой фичи не возникает. Данные страницы наружу не уходят.

**Граница бесплатного и платного:** захват и список тем — бесплатно (мгновенная демонстрация ценности, виральность). Генерация плана и оценка ответов — платно.

### Нужны ли SLM и эмбеддинги на клиенте — нет

Решение зафиксировано, чтобы к нему не возвращаться:

| Задача | Решение | Почему не малая модель |
|---|---|---|
| Разбор вакансии | **Газеттир + эвристики секций** | Закрытый словарь: список технологий известен заранее. Детерминированно, мгновенно, нулевой вес, тестируемо. SLM на этой задаче выдумывает технологии, которых в тексте нет, — и это неотлаживаемо |
| Поиск по вики | **MiniSearch (BM25) + фильтры** | Vectorless RAG на 2 000 чанков с богатыми метаданными; эмбеддинги — только если eval-набор покажет нехватку recall |
| Расширение запроса | Статическая таблица синонимов (тот же газеттир) | Незачем звать модель ради синонимов |
| **Оценка ответов** | **BYOK — полноразмерная модель** | Рубричное оценивание требует качества, которого у малых моделей нет; это платная фича, ошибаться нельзя |

Цена SLM в браузере: в бандл не положить, качать в рантайме сотнями мегабайт, WebGPU есть не у всех, холодный старт секундами — и всё это за качество ниже газеттира.

### Конфликт «локально» × «оценка ответов» — решается BYOK

Оценщик требует LLM. Варианты и вердикт:

- **Локальная модель в расширении** — нежизнеспособна: размер пакета и качество браузерного инференса для нюансированного оценивания.
- **Chrome Prompt API (Gemini Nano)** — device-gated, доступность зависит от железа и версии, качество для рубричного оценивания слабое. Не строить на этом платную фичу. ⚠️ Статус API проверить актуально перед решением.
- **Свой сервер-прокси** — «локальность» теряется, появляется стоимость на каждого пользователя. При нулевом бюджете плохо.
- **BYOK (свой ключ пользователя)** — ✅ рекомендуется. Пользователь вставляет собственный API-ключ, расширение ходит в модель напрямую. Аудитория — разработчики, для них это норма. **Единственная модель, при которой платящий пользователь стоит тебе ноль.**

### Что где живёт

- **Локально в расширении:** весь банк (вопросы, вики, DSA), поиск, интервальные повторения, прогресс. Работает офлайн, без сервера, без сбора данных.
- **Наружу (по ключу пользователя):** только вызов LLM для оценки ответов.
- **Сервера нет вообще.** Обновления контента приезжают обновлениями расширения — магазин сам их и раздаёт.

**Хранение:** контент — бандл в пакете (~660 вопросов + ~180 статей + DSA ≈ несколько МБ текста); прогресс — IndexedDB.
**Поиск:** в расширении SQLite/FTS5 неудобен, поэтому `packages/rag` получает второй бэкенд — `MiniSearch` (BM25 в чистом JS). На 2 000 чанков этого достаточно. Интерфейс поиска один, бэкенда два: SQLite для CLI и сайта, MiniSearch для браузера. **Eval-набор RAG прогоняется на обоих** — иначе качество поиска разъедется между поверхностями.

### Монетизация расширения

**В Chrome Web Store нет встроенных платежей** (собственный биллинг магазина давно закрыт). Значит чекаут внешний в любом случае — это ещё один довод за то, что сайт нужен.

- **Бесплатно:** весь банк, вики, тренировки, интервальные повторения, оверлей на LeetCode. Настоящая ценность, а не демо — иначе не будет ни установок, ни отзывов, а это единственные факторы ранжирования в CWS.
- **Платно:** оценка свободных ответов, калибровка уровня, карта слабых мест, план подготовки, режим «под вакансию».
- **Лицензия — офлайновая, подписанная.** Ключ подписывается Ed25519, публичный ключ вшит в расширение, проверка локальная, без обращения к серверу. Полностью совместимо с «локальностью» и работает офлайн.
- **Риск, который надо принять осознанно:** расширение — клиентский код, офлайн-лицензия снимается тем, кто разберёт бандл. Для продукта такого масштаба приемлемо, но это плата за отсутствие сервера.
- **Модель цены:** разовая покупка ($15–30) ложится сюда лучше подписки — нет сервера, нет повторяющихся затрат, нечего оправдывать ежемесячным платежом.

### Статический сайт — лендинг, чекаут и SEO-страницы

**Пересмотрено 2026-09-06.** Продукт живёт в расширении, но сайт отдаёт статьи вики в индекс.

Один день работы (Astro или Next static, Vercel free tier). Две причины:

1. Единственное место, где может жить чекаут Paddle и выдача лицензионного ключа — в Chrome Web Store встроенных платежей нет
2. Лендинг: листинг в CWS сам по себе конвертирует плохо

**Почему вернул SEO:** при нулевом бюджете это единственный канал, который накапливается. Органика Chrome Web Store ранжируется по установкам и отзывам, то есть требует трафика, чтобы дать трафик — сама себя не запускает. Страницы вики решают эту проблему курицы и яйца: человек ищет «react 19 rsc caching interview», попадает на разбор, ставит расширение. Плюс GEO — размеченный контент с источниками имеет шанс попасть в ответы ChatGPT и Perplexity, а это растущая доля поиска.

Стоит это почти ничего: контент уже структурирован и отделён от доставки, страницы генерируются из того же `content/`.

**Архитектура страниц под SEO/GEO:**
- `/{lang}/wiki/{domain}/{slug}` — статьи вики. **Основной SEO-актив:** голые Q&A-страницы ранжируются плохо, длинный разбор темы — хорошо. Статья + связанные с ней вопросы на одной странице сильнее, чем каждая по отдельности
- `/{lang}/{domain}/{level}/{topic}` — кластеры long-tail
- `/{lang}/q/{slug}` — страница одного вопроса
- `/{lang}/dsa/{pattern}` — паттерны с курируемыми списками задач
- Страницы, генерируемые из карты вакансий (стек × уровень) — уникальный контент, которого нет у конкурентов
- Разметка `FAQPage`/`QAPage` Schema.org, чистая семантика, видимые `sources` — это повышает шанс цитирования в ChatGPT/Perplexity (GEO)

**Языки:** старт `en` + `ru`. `ua` — после подтверждённого спроса; третий язык умножает стоимость ревью без пропорциональной отдачи.

**Биллинг:** Paddle — основной вариант. Merchant of record: сам закрывает VAT/sales tax по миру, выплаты на Payoneer/Wise, поддерживает подписки и разовые продажи. Запасные, если Paddle не примет юрисдикцию: FastSpring или Gumroad (тоже MoR, Gumroad проще и дороже по комиссии). `monetize.software` — тоже MoR, но малоизвестен, выше риск на приёме платежей с Запада. Stripe напрямую — проверить доступность по юрисдикции; при прямом Stripe VAT ложится на тебя.

Не «3 дня бесплатно»: реальный паттерн — человек готовится к одному собесу и уходит. Региональные цены обязательны.

**Организационное по Chrome Web Store** (⚠️ политики меняются — сверить перед подачей): разовый взнос разработчика; обязателен MV3; удалённый код запрещён; вкладка Privacy заполняется по факту (при отсутствии сбора данных — тривиально); широкие host-permissions удлиняют ревью. Тот же MV3-код с минимальными правками принимают Firefox Add-ons и Edge Add-ons — дополнительный охват почти бесплатно.

**Дистрибуция без бюджета:**
- SEO статей вики — основной канал, единственный, который компаундится
- Оверлей на LeetCode — виральная механика внутри целевой аудитории, она же питает органику CWS
- **Один** community-канал под нишу. Reddit/Habr/Telegram/Medium одновременно при нулевом бюджете = ноль везде

### Разбор репозитория кандидата (GitHub / GitLab / Bitbucket)

Сценарий: кандидат указывает GitHub в резюме, интервьюер его открывает и идёт по нему вопросами. Расширение отвечает на вопрос «что он там увидит и что спросит».

**Главное — не оценка кода, а генерация вопросов.** Репозиторий превращается в персональный набор вопросов, который попадает в тот же тренажёр со SM-2 и к тому же оценщику. Без этого фича вырождается в ещё один линтер, каких много.

**Доступ — BYOT, по аналогии с BYOK.** Страница репозитория показывает только дерево файлов, поэтому нужен публичный REST API площадки. Без токена GitHub даёт около 60 запросов в час на IP — не хватает; с токеном пользователя лимит на порядки выше. Токен хранится локально, как и ключ LLM.

**Два слоя:**

**1. Эвристический — бесплатный, без LLM.** Проверки ровно того, на что интервьюер смотрит в первые две минуты:
- README: есть ли, есть ли инструкция запуска, описание архитектуры
- тесты и CI: есть ли вообще, настроены ли
- история коммитов: осмысленные сообщения против «fix/update»; один гигантский `initial commit` — отдельный флаг
- структура: god-файлы как выбросы по размеру, мёртвые директории
- гигиена: закоммиченные секреты (regex-скан), `.env`, `node_modules`, отсутствие lock-файла, вменяемость `.gitignore`
- процесс: PR-ы или прямые пуши в `main`
- наличие Docker/деплой-конфигурации, лицензии

Закоммиченный секрет — красный флаг, который срезает кандидата на месте; одна эта проверка окупает фичу.

**2. LLM-слой — платный, BYOK.** Читает код ключевых файлов → «вот 8 вопросов, которые по этому репозиторию зададут, с ожидаемыми ответами» + «вот слабые места и как их объяснить вслух». Сгенерированные вопросы уходят в общую очередь повторений.

**Отбор файлов — обязательная часть, а не деталь.** Целиком репозиторий в модель не отправить. Приоритет: точки входа, конфигурация, самые большие файлы, самые изменяемые файлы (по статистике коммитов). Здесь впервые появляется смысл в индексаторе символов, но в браузере полноценный граф не построить — хватает файловых эвристик, при необходимости `tree-sitter` в wasm.

**Приватность — говорить прямо.** Для приватных репозиториев нужен токен с доступом к коду, и код уходит **в собственного LLM-провайдера пользователя**. Это должно быть написано в интерфейсе открытым текстом до первого запроса, а не спрятано в политике. Утверждение «мы не собираем данные» остаётся верным (ты действительно ничего не собираешь), но переоценивать его нельзя.

**Почему не в Фазу 1.** В Фазе 1 уже расширение, оверлей на LeetCode, захват вакансии, оценщик, сайт и лицензирование. Добавление сюда разбора репозиториев означает не выпустить ничего. Если фича нужна раньше — брать **только эвристический слой** и вычёркивать что-то другое, а не добавлять сверху.

### Остальное в Фазе 2

Второе направление — выбирается **по данным**, а не по вкусу: карта частотности вакансий к этому моменту накоплена и покажет, что востребовано рядом. Инфраструктура переиспользуется целиком, добавляются только статьи и вопросы. Тогда же публикация в Firefox Add-ons и Edge Add-ons — тот же MV3-код с минимальными правками.

## Верификация

**Фаза 0:**
- `make check` (обёртка над pnpm — единая поверхность команд для харнесса) — Zod-валидация всего `content/`; CI падает на невалидной схеме, на битой ссылке в `related_questions`/`related_concepts`, на `draft` в продовой выборке
- Валидация DSA-задач: у каждой `task` заполнены **оба** подхода, `key_insight` непустой, и асимптотика `optimal` строго лучше `naive` (сравнение по нормализованному классу сложности) — иначе задача не учит переходу и не проходит CI
- Юнит-тесты SM-2: известная последовательность оценок → ожидаемые интервалы
- Тест оценщика на **золотом наборе**: 20 заранее размеченных пар (ответ, ожидаемая оценка уровня); совпадение замеряется при каждом изменении промпта. Без этого набора калибровка недоказуема.
- **Eval-набор RAG**: 50 пар (запрос → чанки, обязанные попасть в топ-K), метрики recall@k и MRR. Прогоняется при каждой правке чанкинга или ретривера. Именно он даёт основание переходить на эмбеддинги — или не переходить.
- Проверка заземления: доля ответов режима обучения с валидными цитатами = 100%; ответ без цитат — баг, а не «модель так решила»
- `wiki lint`: битые `[[ссылки]]`, циклы в `prerequisites`, статьи-сироты, вопросы с `wiki_refs` на несуществующий якорь, расхождение `wiki_reviewed_at` с `reviewed_at` статьи
- Проверка карты частотности: топ-10 доменов из вакансий сверить вручную с 20 живыми объявлениями
- **Лицензионный гейт импорта:** CI падает, если в контенте есть элемент с `provenance` на источник без `commercial_ok: true`; отчёт по требуемому авторству генерируется автоматически
- Отчёт дедупликации после каждого импорта + доля импортированного, пережившая ревью. Если у источника выживает <30%, он не окупает время — вычеркнуть
- Реальная проверка: 2 недели тренировок, сверить карту слабых мест с ощущениями на настоящем собеседовании

**Фаза 1:**
- Lighthouse SEO + валидация разметки Schema.org
- Проверка, что страницы вопросов рендерятся статически и доступны без авторизации
- Тестовый платёж в sandbox выбранного MoR + выдача лицензионного ключа
- **Расширение:** eval-набор RAG прогоняется на MiniSearch-бэкенде и сверяется с SQLite — расхождение recall@k выше порога блокирует релиз
- Проверка офлайна: расширение с отключённой сетью даёт полный банк, поиск, повторения, прогресс **и разбор вакансии**; наружу уходит только вызов LLM по ключу пользователя
- **Газеттир на золотом наборе вакансий:** 30 сохранённых страниц с размеченными вручную технологиями, уровнем и делением required/nice-to-have. Метрики precision/recall по извлечению; регресс блокирует релиз. Отдельно проверяются отрицания и границы секций — там ломается чаще всего
- Проверка на площадку: смена вёрстки djinni/LinkedIn не должна ронять расширение — при несовпадении селекторов срабатывает generic-фолбэк, а не пустой результат
- Проверка лицензии: подделанный ключ отвергается, валидный работает без сети
- Ревизия манифеста перед подачей: только точечные host-permissions, никаких `<all_urls>`, отсутствие удалённого кода
- Отслеживание: индексация страниц, позиции по long-tail, конверсия в оплату
